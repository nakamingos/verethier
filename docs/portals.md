# Bouncer portals

## First release: admin control room

Open `https://bouncer.up.railway.app/admin` and sign in with Discord. Only server owners and current administrators can manage a server. An OAuth server list is used for navigation; Bouncer fetches the actor's current membership and permissions again for each server operation.

Discord sign-in and sign-out share the header on Control Room and Help, including direct Help visits and reloads. They use a shared in-memory session and CSRF-protected logout; a failed logout retains the signed-in account. Sign-in appears when configured and signed out; sign-out shows the signed-in username and retains busy-state protection. The heading reads “[Server name] Control Room” in one font size, followed by the rule count; logout or session expiry hides the server summary. Header and ordinary admin buttons share the server toolbar frames, while tabs, dropdowns and member suggestions keep their dedicated styles. Keyboard focus uses an underline, with system outlines in high-contrast mode.

The control room provides rules with asset filters and search, create/edit/delete forms, review before saving, Undo/Redo, bot settings, verification-message controls, member lookup and paginated activity. Rules keep today's asset capabilities and count-combining behavior. The existing `/setup` commands remain available. `/help` and `/join` are member-facing shortcuts; Discord may need a reload after commands refresh.

Audit Log opens immediately without dimming the tabs or showing a loading indicator. Refreshes keep the current entries until fresh data arrives, and navigating away cancels the pending read.

Edit opens beneath the selected rule, extending the same card frame without a drop shadow. The expanded frame uses the blue indicator band on both its upper and lower sections; Review changes is vertically centered with the editor title. Its Edit button becomes Cancel and discards unsaved changes. Combined badges sit to the right of Edit/Delete on the same row, with a shorter label in narrow cards. They and the Rule group filter show collectible rules sharing a channel, role and minimum. A group view includes all contributors across asset types and provides links to each rule. ERC-20 balances do not combine with collectible counts.

Add rule toggles the creation form without discarding its choices or review state. Drafts are retained separately for each server within the current control-room session, including navigation between tabs and servers. Cancel discards a draft; saving creates the rule and clears it. Review changes appears to the right of Cancel. New rules default to Ethscriptions; asset menus list Ethscriptions, Ordinals, NFTs and Tokens (ERC-20), with All assets retained for filtering.

Cards keep equal heights and actions aligned at the bottom. Changing button labels reserve their largest size. Holding a button or tab keeps its position, size and bevel unchanged; hover, focus and selected states remain distinct. Disabled buttons keep their solid frames and use muted text rather than fading the entire control. Item counts use the reference's 14×16 raised display frame, with its six-row lower bevel preserved in the border-image slice. The theme switcher fits the supplied 10×10 icon at 2× scale inside a 34px square tool button aligned with the header controls and inverts it in light mode. Field and dropdown titles end in colons. Notifications use a fixed, dismissible area with Undo/Redo. Server loading retains the current view, makes it inert, and replaces the server ID and data together only after a successful response; initial loads show static placeholders. Audit results scroll within a stable area so pagination stays in place. The primary font is preloaded to reduce text reflow. Content panels and form gaps are tighter; server-menu and tab spacing is unchanged.

Button contents sit one pixel higher, while workspace-tab text sits one pixel lower without changing control dimensions. The footer has no top separator, and the last previously earned role has no trailing separator.

Shared controls use solid two-pixel border bands in both themes: raised buttons with two short corner cuts and a lower ledge, recessed fields, shallow card frames, and tabs with stepped shoulders and flared active feet. Nine-slice SVG frames keep the corner steps fixed without changing control dimensions or clipping editors, suggestions or keyboard focus. Dropdowns share a select-only combobox with the sampled field and arrow frames, a blue menu outline and gold option highlight. Keyboard navigation scrolls only inside the popup and preserves its scroll position during viewport updates. Arrows, Home/End, Page Up/Down and type-ahead navigate options; Enter/Space/Tab commit, and Escape cancels. The Popover API keeps menus above inline editors and dismisses outside clicks; menus sit directly against the trigger, fit the viewport and open upward when needed. The arrow is 22px wide within a 34px square button, matching the default control height. Text fields and dropdowns retain their font sizes with tighter padding, a 2px label gap and 24px single-line menu options. Angular form values, null choices, required fields and disabled roles retain their original behavior. High-contrast mode uses system colors and plain borders.

The admin tabs join a shared workspace surface that spans the screen. The server menu and every tab's content sit inside it, with the menu remaining sticky on desktop. Content retains a readable maximum width; on mobile the tabs scroll in one row so the active tab stays connected to the surface. Initial loading uses the same outer layout.

Dropdowns use 18px text and compact, centered rows. The field extends beneath the two-step arrow button, and open menus have no shadow or opaque corner background. The outer corner pixel is transparent and its two neighbors are translucent. Keyboard focus underlines the closed value; the blue frame belongs only to the open menu.

Tab frames preserve the source sprites' asymmetric right edge and flared active feet. The dark palette uses direct PNG pixel samples: active face `#333333`, active rim `#575757`, inactive face `#202125`, inactive rim `#2f3136`, and black outlines. The original theme definitions provide the strip color `#2c2c30`, active text `#c0c0c0`, and inactive text `#7d7d7d`. These values are explicit, not calculated tints.

The server menu uses the source editor frame: a `#202125` interior, black inner border, `#2b2b2b` upper rim and `#575757` left/lower rim. Server controls use the tool-button frames with `#292b30` faces and `#41444a` bands; the current server has the lighter `#41444a` face and `#202125` lower inset of the selected tool. Selection is also marked with `aria-current`. Light mode uses the same geometry with its light palette.

Server buttons and invite links use equal avatar slots and heights, with initials when an icon is missing. Names stay on one line with an ellipsis and a full-name tooltip. Server buttons match the default 34px height and 16px text, with 22px icons or initial slots. Invite entries for servers without Bouncer use #999B9F text.

Servers with Bouncer installed appear first. Both installed and invite groups sort by name without case sensitivity and with numeric ordering (2 before 10). Rule search and member lookup use the supplied `search.png` unchanged at 2× scale inside their fields, with space reserved before the text. Text fields use the reference's recessed frame and blue focus border with gold text selection; focusing a field keeps its dimensions fixed.

Stacked server buttons overlap their bottom outline and shadow with the next top outline, leaving one shared divider. Cards across Rules, Bot Settings, Member Lookup and Audit Log use the reference editor frame with black inner/outer outlines, a `#41444a` rim and a `#202125` interior. Combined-rule and editor highlights retain their accent, with joined open/lower frames keeping inline editors continuous. Light mode retains the same geometry.

Border geometry and reference palettes are adapted from the [Aseprite Default themes](https://github.com/aseprite/aseprite/tree/main/data/extensions/aseprite-theme) by David Capello, Ilija Melentijevic and Nicolas Desilets, licensed under [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). Bouncer reconstructs the frames as SVG grids, recolors them to its themes, and adds card/editor variants; the theme toggle and checkbox use the supplied PNG assets (both supplied 9×9 checkbox icons).

Member Lookup accepts Discord IDs, usernames and server nicknames without case sensitivity. Suggestions show the username and ID to distinguish shared names. Only an exact, unique name or a selected member resolves; Bouncer confirms current server membership before exposing saved information. Direct ID lookup remains available if Discord member search is unavailable.

The same field accepts a full EVM or Bitcoin mainnet Taproot Ordinals wallet address. Exact address matches include current saved links and retained link/verification/removal/transfer history, with current and historical matches labeled separately. Every matching account must still be a live member of the selected server; unrelated or former members' identities are not returned by lookup. Multiple matches require an explicit member choice, including when submitting before autocomplete finishes. Incomplete addresses are not prefix searches, Bitcoin checksums and original letter casing are validated before normalization, and reads start no ownership scans. Associations predating retained wallet history may be missing.

Member Lookup loads saved information first. Check Roles fetches current ownership. Fix queues reconciliation of previously earned roles only. Provider uncertainty retains roles. Background checks default to enabled; disabling them skips scheduled role checks for that server. Explicit verification, rule changes and requested repairs still reconcile earned roles. New qualifiers must verify.

Member Lookup separates current saved wallets from removed/transferred wallets. Both tables show Last proven and link the shortened address to Etherscan or the Bitcoin explorer; the full address remains in its tooltip. Removed rows include the removal/transfer time. Re-added addresses appear only in the current table. Removal retains the wallet's proof timestamp before deleting the active link. Older removals without a retained proof date show Unknown. Admin authorization and current target membership are checked before returning either table; removed wallets never contribute to eligibility.

Both wallet tables show the address's block status in the selected server and offer Block/Unblock. A review displays the full address, server and optional reason before confirmation. The restriction, audit receipt and durable earned-role checks commit together. Checks target the address's current linked account, including when a historical address has transferred, without exposing that account's identity. Saved links remain intact; other eligible wallets still qualify, other servers are unaffected, and unblocking does not grant new roles. Retrying the same request creates no duplicate work or reapplies a superseded restriction. Wallet restrictions appear in Audit Log → Changes; use Unblock or Block rather than rule Undo/Redo to change them.

Member Lookup also offers **Audit member** and **Audit all members** for shared-wallet history. Reports match exact addresses across saved links and retained wallet activity, deduplicate repeated events for the same account, and show first/last recorded dates, last proof and current-link state. Current Discord members and former members with saved server-specific records are included; identities with no membership or saved history in this server are excluded. Wallet and account results both paginate. Audits read saved evidence and start no ownership scans or moderation actions. The displayed history start makes incomplete older transfer history explicit. Discord must allow Bouncer to list server members (Server Members access in the application settings); enumeration failures return an error rather than a partial clean report.

Rules → **Role actions** configures “when Bouncer grants or restores this role, remove these roles.” A review previews the server, trigger and selected removals, including application to previously tracked holders. Each server/trigger pair has one action with up to 20 target roles; roles must be manageable, self-removal and cycles are rejected, and stale edits conflict. Bouncer suppresses grants/restoration of target roles while a trigger is held. These actions respond to Bouncer grants/restorations, rather than general Discord role events. Targets can include roles Bouncer did not originally assign. Removing the trigger does not restore arbitrary roles; ordinary checks can restore eligible previously earned roles once the exclusion ends.

Role-action settings and their checks appear in Audit Log. Grant tracking durably queues removal work in the existing reconciliation queue, with permission failures retried and failed jobs available for Retry check. Removing a policy cancels pending removals under it and queues earned-role checks. A newer policy change keeps a separate receipt/job even when a prior grant job is pending. Migration `20261018040000_role_actions_wallet_audits.sql` adds the private settings table, queue dispatch field and backend-only audit/mutation functions; rehearse it with `python3 backend/test/check-role-actions-audits.py BACKUP_DIRECTORY [GUARDED_APPLY_FILE]`.

Migration `20261018030000_portal_wallet_blocks.sql` adds a backend-only transaction function over the existing blocklist, audit and reconciliation tables. Rehearse it against a private backup with `python3 backend/test/check-portal-wallet-blocks.py BACKUP_DIRECTORY [GUARDED_APPLY_FILE]` before the guarded upgrade.

Rule changes from both interfaces queue durable checks. A dashboard rule mutation, its revision and its check job commit together. Stale edits are rejected. Undo/Redo reverses the definition and evaluates current ownership, including alternative rules and saved wallets. Restoring a deleted rule preserves its ID. Undoing a new rule does not delete its Discord role.

The dashboard can also change a rule's role or create a missing role. The review shows the old and new roles. This explicit administrator action automatically checks previous holders of the old role against the changed rule's new channel/minimum group and grants the new role when eligible. Existing holders of the new role retain their alternative qualifying paths. The old role is checked against its remaining rules before removal. This does not grant roles to unrelated members. Undo/Redo uses fresh checks and the same audience; a created Discord role remains available after Undo.

Role-change jobs add `rule_id` and `member_ids` to the existing reconciliation table. The audience is captured in the same transaction as the edit and carried forward across rapid edits and reversals, including pending or interrupted moves. These columns contain the affected Discord IDs, not wallet metadata or collection inventories. They retain the table's backend-only access.

Role checks display pending/running/completed/failed states and results in Audit Log → Role checks. Interrupted jobs use leases; unavailable checks retry at five-minute intervals, up to three attempts. Failed jobs have a Retry check action. The bot never treats an unavailable provider as a zero balance.

Rules sort numerically by rule ID in either direction, including combined-group views. Activity sorts by date (newest first by default), with an ID tie-breaker, before server-side pagination. The Servers heading uses the dropdown-label color and sits above the menu; avatar slots have transparent backgrounds. Counts and status indicators share the stepped light-rim display frame. Bot Settings dropdowns have a wider 32rem preferred width. Their actions align to the right of their dropdowns and wrap to the right on small screens. Save settings, Update message and Check again reserve the widest of their labels so all three buttons have the same width. Activity pagination groups Previous, Next and Last together on the right; Last jumps directly to the final page.

## Installation and Check Setup

After using a server's invite link, return to the portal and use **Refresh servers** to select the newly installed bot. A server without rules opens Bot Settings with Channel setup first.

**Channel setup** can select existing text channels or create a private admin channel and a member verification channel. New admin channels deny ordinary members access; server administrators and Bouncer can view them. New verification channels allow members to view/read while disabling ordinary member message posting. Existing channels retain their permissions. Creating channels requires Manage Channels plus Bouncer's message permissions; selecting existing channels does not require Manage Channels. The review shows names, permission choices, the new default verification channel and any messages to post before **Confirm setup**. It never moves existing rules between channels. The admin channel's Control Room link still requires Discord login and current owner/Administrator authorization.

Setup previews expire after ten minutes if not started. Confirmation checks live admin permissions before each Discord mutation, records progress privately, and serializes setup within a server. A lost response can be resolved from the saved receipt; partial setup can be continued after reload by its original actor. Created channels are recovered by saved ID or their setup topic marker. If a Discord creation/post has an uncertain result, retries first search for its resource and do not blindly send another create request. **New review** leaves any created channels available for explicit selection. Channel settings changed by another admin cause a conflict; background-check settings are preserved. Completed setup and recovery appear in Audit Log → Changes without rule Undo/Redo actions.

**Check setup** runs only when requested. It refreshes the bot member, roles and channels, checks role hierarchy/manageability and channel permissions, then checks verification messages and the providers used by current rules. Results include affected rule IDs and actionable fixes. Message searches cover recent history, pinned messages and up to 1,000 messages per channel. A failed/incomplete search is unavailable, not evidence of a missing message; pin an older verification message and retry. Missing-message results offer **Review recovery**, which checks again before confirmation and reuses a message that has appeared meanwhile. The verification-message form's **Recover missing** action uses the same reviewed, durable path. Setup checks never change member roles or scan member wallet inventories.

Provider results distinguish reachable, unavailable and not checked. RPC probes verify network identity and a latest-block read; data/metadata/collection probes check a bounded read rather than complete eligibility. Ordinals number inventories require a member **Check Roles** and are explicitly not checked by setup. Collection connectivity does not guarantee wallet-inventory or individual-token availability. Provider failures retain the existing eligibility engine's unavailable behavior.

Administrators also get a **Check Setup** button from Discord `/help`. The button validates current owner/Administrator permissions on every click and returns an ephemeral summary, with the full report and reviewed repairs in the portal. Existing `/setup` commands remain available.

Migration `20261018050000_setup_assistance.sql` adds the optional admin-channel ID and backend-only setup plans/progress. It does not rewrite rules, wallet links or assignments. Rehearse against a fresh private backup with `python3 backend/test/check-setup-migration.py BACKUP_DIRECTORY [GUARDED_APPLY_FILE]`; the checks cover preservation, scope/replay, preview expiry, worker leases, settings conflicts and a concurrent first settings insert. Browser coverage is `yarn --cwd frontend test:setup-smoke`.

Discord references: [channel creation permissions](https://docs.discord.com/developers/resources/guild#create-guild-channel) and [message nonces](https://docs.discord.com/developers/resources/message#create-message).

## Deployment

The frontend remains a static Caddy site. Its `Caddyfile` forwards `/api/*` to the backend over HTTPS. Portal cookies stay on the frontend origin. Existing signed verification endpoints still work at the backend's public URL.

Backend configuration:

- `BASE_URL=https://bouncer.up.railway.app`
- Matching `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET` and `DISCORD_BOT_TOKEN` from the Bouncer Discord application.
- Discord OAuth2 redirect: `https://bouncer.up.railway.app/api/portal/auth/callback`.
- Existing database service-role and verification provider settings.

Discord login uses `identify guilds`. Access tokens are discarded after login. The database stores one-time OAuth state hashes and opaque web-session hashes; secure, HttpOnly, SameSite cookies expire after eight hours. Mutations require the exact frontend Origin and a session-bound CSRF header. Protected data is never cached. New tables/functions allow backend service-role access only. Signed-in portal rate limits use the authenticated user ID; unauthenticated traffic retains conservative IP limits. Arbitrary forwarding headers are not trusted.

For development, proxy `/api` to a local backend through the frontend dev server and set `BASE_URL` to that frontend origin. Use a separate Discord redirect/client configuration for development.

Before the schema upgrade, create private roles/schema/data dumps and test restoring them. `backend/test/check-portal-migration.py BACKUP_DIRECTORY` restores the application data in a disposable database, checks that the migration preserves all values, and exercises transaction/replay/version/Undo/Redo/job/permission behavior. Production history predates the repository's migration files, so do not repair or erase that older history just to make `db push` proceed. Apply the tested new migration and record only its version in one guarded transaction.

## Member portal

Open `/member` from the footer or Help. Discord sign-in returns members to their account, with **Overview**, **Wallets**, and **Communities**. Counts and previously earned roles come from saved records; opening the dashboard never starts ownership scans. Communities lists joined servers with Bouncer, rechecks live membership, and shows rules only for channels the member can view. A temporarily unavailable community does not prevent wallet management. Sign in again after joining another server to refresh Discord's server list.

Wallets supports copy/view, adding EVM or Bitcoin mainnet Taproot Ordinals wallets through the existing EVM/Xverse/UniSat connection and signing services, and **Remove wallet from Bouncer**. Linking requires a fresh, ten-minute account-bound proof with a distinct wallet-link purpose. EVM messages also bind the frontend origin and exact address. Linking does not award community roles or bypass server wallet blocks. If a wallet belongs to another account, its fresh proof must be followed by explicit transfer confirmation; previous-account role checks are queued without exposing that account's identity or communities.

Removal previews communities with previously earned roles. The wallet deletion, activity record and per-community reconciliation jobs commit in one transaction. Other wallets remain linked. The existing previously-earned-only engine checks all remaining qualifying paths, preserves roles on provider uncertainty, and retries failed changes. Wallet activity shows durable progress with Refresh and Retry check; repeating a removal request does not enqueue duplicate work. Closing a wallet app is separate from deleting its saved Bouncer link.

Communities uses the configured default verification channel, or asks the member to choose. Verify opens the existing personal verification page and checks only that channel for new roles; earned-role reconciliation retains its existing broader alternative-rule checks. EVM and Bitcoin proofs are consumed before changing a wallet link, so concurrent submissions cannot replay a proof. Existing direct Discord links and approved EVM connections continue working.

The Communities search field uses the supplied pixel search icon and the shared light-mode inversion.

Each community has a Show roles switch for Available roles and Earned roles. Earned means the account has an active saved assignment; Available includes configured roles without an active saved assignment, marking past earnings separately. Results stay scoped to the selected visible channel, with requirements grouped by role ID and channel so shared names and combined rules remain distinct. Switching views/channels reads the loaded summaries and starts no ownership scans.

Wallet activity records links, transfers, removals, and successful manual verification from both Discord and the portal. Entries show the entry point and visible community/channel where applicable. Repeated proofs of an already-linked wallet do not create extra Linked entries; successful role verification gets its own Verified entry. Proof-valid links remain recorded even if eligibility fails. Transfers appear in the previous account's history without exposing the destination identity or community. Automatic background role checks remain in the role audit log. The new records begin with this release; earlier Discord events cannot be reconstructed as a complete history.

Migration `20261018020000_unify_wallet_activity.sql` adds source/context and retained proof timestamps to existing activity records. The verification link RPC commits wallet changes, history and prior-owner reconciliation jobs together. Rehearse it using `python3 backend/test/check-wallet-activity-migration.py BACKUP_DIRECTORY`. New tables, inventories and metadata catalogs are unnecessary.

One pending account flow is saved on the backend. Continue rechecks identity/context and expiry; an invalid challenge is replaced with a fresh one. A completed verification marks only its matching pending flow complete. Not now hides the banner for the current visit and leaves the flow available after a reload. Wallet signatures are never persisted in the browser or database.

The member migration adds only flow/action bookkeeping and links to the existing reconciliation queue. It does not add an inventory or metadata catalog. Rehearse `20261018010000_add_member_portal.sql` against a private backup with `python3 backend/test/check-member-migration.py BACKUP_DIRECTORY` before applying the guarded upgrade. Run `yarn --cwd frontend test:member-smoke` for desktop/phone signing, transfer, removal/retry, joined-community verification and resume coverage.

## Following releases

Optional ideas are tracked in the [optional feature backlog](plans/optional-features.md).

Public discovery, optional add-ons, additional networks and broader wallet/address support remain deferred.

The rule editor supports up to ten trait conditions on NFT, Ordinals and Ethscriptions collection rules. Choose AND to require every condition on the same collectible, or OR to accept any condition. Matching is case-insensitive; `ALL` as a value accepts any value for that key. Remove all conditions for quantity-only rules. OR counts an asset once, and ERC-1155 matching copies retain their quantities. Conditions do not combine across different assets. Nested groups are not supported.

The editor retains conditions when Add rule collapses a draft. Review/Save, edit, Undo/Redo and duplicate detection use the full predicate. Discord add commands keep their existing single-trait options; multi-trait rules display every condition, and the simple Discord edit modal directs administrators to the Control Room instead of truncating the rule. ERC-721 ID lists/ranges and quantity thresholds remain the next milestone; current single-ID restrictions still apply.

Migration `20261018060000_multi_trait_rules.sql` backfills canonical `trait_filter` JSON and its normalized identity without changing IDs, assignments, proof history or single-trait snapshot hashes. Database triggers guard legacy single-trait input/projection columns, prevent single-field edits from truncating multi-trait rules and invalidate stale Ordinals snapshots. Those projection columns are temporary rollout compatibility, not a second authoritative definition; physical removal remains a follow-up after older application versions are retired. Apply the migration before releasing the new backend/editor. Do not create multi-trait rules while an older verification worker remains active.

Rehearse with `python3 backend/test/check-multi-trait-migration.py BACKUP_DIRECTORY [GUARDED_APPLY_FILE]`. The harness checks application-value preservation and exercises canonicalization, duplicates, legacy inputs, portal edits/Undo, snapshot invalidation and permissions. `node frontend/test/multi-trait.smoke.cjs` covers complete edit payloads and draft retention at desktop and mobile widths.

## Theme reference colors

Light mode uses the Aseprite Default light theme's XML colors and sampled sheet pixels: header `#d3cbbe`, workspace/active tab `#7d929e`, tab rim `#adcade`, button/card face `#c6c6c6`, selected toolbar shade `#7c919d`, white fields and highlights, black text/outlines, inset rim/separators `#958174`, inset shade `#7c7c7c`, and menu selection `#ff5555` with white text. Frame geometry stays shared between themes. Search icons invert in light mode; the supplied 9×9 check icons render at 2× and invert in dark mode. Table dividers use a 2px-high repeating 4px dash / 2px gap, with no trailing divider after the final entry.

Mobile header links retain the same side padding as default buttons. Navigation aligns beside the title where it fits and wraps intact on very narrow screens; authentication remains right-aligned below.

Light dropdowns have white outer/focus rims, white field/menu faces, coral selection with white text, black text/arrows, gray (`#c6c6c6`) arrow buttons, white button highlights and `#7c7c7c` button shading. Brown (`#958174`) inset/corner pixels remain distinct from the white rims. The theme toggle keeps ordinary button chrome in both themes; its `aria-pressed` state does not apply selected-server colors.

Field titles use a compact 20px line height and no extra top margin before their dropdowns or text inputs; control heights and font sizes remain unchanged.

Light mode has no visible header divider. Expanded rules and the Add rule form use white frame highlights. The server menu matches the light editor frame: `#655561` interior, `#645460` upper rim, `#adcade` side/bottom highlights, black outline, and workspace-colored outer corners.

Dropdown pointer activation and hover feedback are restricted to the arrow. The value area keeps its appearance and does not open the popup on a pointer click. Keyboard and assistive activation retain the existing selection, type-ahead, Escape and Tab behavior.

The strip immediately inside the top black outline uses `#c6c6c6` in light mode, independently of the darker outer inset rim. Text entries and dropdown fields share this lighter inner shadow.
