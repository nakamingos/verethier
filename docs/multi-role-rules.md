# Duplicate rules and multiple role outputs

In Control Room → Rules, **Duplicate** opens a separate draft containing the source rule's complete requirements, including inscription IDs or number ranges, traits, minimums and network/asset settings. Choose an existing role or enter a new role name, review, and save. The copy receives its own rule ID. Editing either rule afterward does not change the other. Saved wallets, assignment history and role-removal policies are not copied. A stale source draft must be reloaded; retries reuse the existing action rather than creating another copy.

In new or existing rule editors, the **Discord roles** dropdown uses checkboxes to select every role granted by the same requirements. The menu stays open while selecting multiple roles. Choose **Create a new role…** inside the menu to enter a new role name. Uncheck a role to remove it from the rule; at least one role must remain selected. A rule supports up to 20 distinct outputs; Bouncer cannot assign managed roles, @everyone or roles above its position. The original `role_id` remains the primary output for compatibility, and `additional_roles` stores the remaining IDs and fallback display names on that same rule row. Current labels come from Discord; renaming a role does not change eligibility or edit versions.

Verification reads ownership once per rule within a run and evaluates each output independently. Combined-count groups continue to use role, channel and minimum; adding an output does not combine it with unrelated roles or double-count an asset. Existing role exclusions and role-removal policies still apply. Background checks, Fix earned roles, bulk role checks, member community listings and export eligibility understand additional outputs. A selected-rule bulk check grants every output of that exact rule; all-rules mode preserves alternative and combined paths.

Adding an output to an existing rule queues fresh checks for the server's previously Bouncer-earned holders of the original outputs, including the pending audience from rapid earlier edits. It does not grant solely from Discord role possession. To include current Discord role holders who have no Bouncer-earned history, use **Bulk role check → Current role holders**. New duplicate rules do not automatically enroll all holders of the original rule's roles.

Removing an output or deleting the rule queues each affected role for reconciliation. Another qualifying rule preserves the role; unavailable ownership providers do not justify removal. Undo/Redo restores the output list and queues the same checks. Historical action snapshots retain their recorded names. Identical requirements with overlapping outputs are rejected, including when an output is secondary on another rule.

Apply `backend/supabase/migrations/20261108010000_multi_role_rules.sql` before deploying this release. No new environment variables or user signatures are required. Existing single-role rules keep their IDs, requirements and primary roles, and their additional-output lists start empty. Existing single-role version hashes stay stable. Refresh an editor after upgrading before adding outputs.

Validation includes backend multi-role and duplicate regression tests; production builds; `npm run test:multi-role-smoke` in `frontend` at desktop/tablet/mobile widths; and `python3 backend/test/check-multi-role-migration.py PRIVATE_BACKUP_DIRECTORY`. The database rehearsal checks original data preservation, role-list validation, overlap rejection, independent range copies, stale writes, Undo/Redo, reconciliation audience and RPC permissions using a disposable PostgreSQL instance. It never changes the remote database.

## Specific inscription contributions

A single inscription ID or number may use a minimum greater than one so it can contribute to a combined group. For example, a rule selecting number 10100838 with minimum 5 contributes one distinct owned inscription; the member still needs five distinct matches across the applicable rules. Keep the same role, channel and minimum across contributing rules. Overlapping selections count an inscription once, and the single-number rule cannot qualify someone alone.

The selection's capacity no longer limits the saved minimum. This permits building the group one rule at a time, consistent with ERC-721 selections. Positive safe-integer minimums, valid canonical IDs, range ordering and the 1,000-selection limit still apply. Create, edit, duplicate and Undo/Redo retain the chosen minimum.

Migration `20261109010000_combined_inscription_minimums.sql` updates only the inscription-criteria validator and rewrites no saved rules or assignments. Apply before deploying the backend change. Rehearse against a private backup with `python3 backend/test/check-combined-inscription-migration.py PRIVATE_BACKUP_DIRECTORY [GUARDED_APPLY_FILE]`.

Portal input errors now distinguish trusted validation messages from unexpected service failures. Invalid ranges or minimums show specific input guidance with HTTP 400; unexpected provider/database errors remain sanitized with retry/operator guidance. Provider URLs, credentials and raw database details are never copied into the response.
