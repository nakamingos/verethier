# Bouncer Frontend

Angular app serving the verification page (`/verify/:data`), the admin Control Room (`/admin`), the member portal (`/member`), help (`/help`), the privacy policy (`/privacy`) and wallet diagnostics (`/wallet-check`).

## Stack

- Angular 21
- TypeScript 5.9
- SCSS
- Reown AppKit 1.8.24 with Wagmi Core 2.22.1 / Connectors 6.2.0 and viem (EVM)
- Sats Connect and UniSat (Bitcoin), Wallet Standard / Phantom (Solana)

## What It Does

- Opens verification links generated by the Discord bot and resolves their context
- Connects EVM wallets through AppKit (WalletConnect, injected/EIP-6963 wallets, Coinbase Wallet and Base Account) and signs EIP-712 proofs
- Connects Xverse or UniSat for Bitcoin (Taproot for Ordinals; legacy/SegWit also for Stamps) and Phantom for Solana
- Hands mobile users into the UniSat or Phantom app browser when needed
- Hosts the Discord-authenticated Control Room and member portal, which call the backend through `/api`

## Requirements

- Node.js `22.12+` (22.x)
- Yarn `1.22.x`

Install dependencies:

```bash
yarn install
```

Run the Angular dev server:

```bash
yarn ng serve
```

Then open `http://localhost:4200`.

### Browser smoke tests

Each suite in `test/` drives the production build in Chromium (set `CHROME_BIN` if it isn't found), using simulated wallets, mocked backend responses and relay traffic. They use no real wallets or API credits, and write screenshots to a temporary directory. Build first, then run a suite with `node test/NAME.smoke.cjs` (several also have `yarn test:*-smoke` aliases):

- `wallet-connection`: EVM signing on desktop/mobile, session restore, Base Account network choice, Android Rainbow app links and retries
- `member`, `portal`, `portal-history`, `setup`, `privacy`, `bulk-role`, `multi-role`, `multi-trait`, `erc721-selections`, `nft-collection`: Control Room and member portal flows
- `solana`, `solana-compressed`, `solana-editions`, `stamps`, `stamps-wallet`: Solana and Stamps rules and signing
- `indexeddb-recovery`: wallet SDK browser-storage recovery

AppKit and Wagmi restore approved EVM wallet sessions together across visits. Wagmi also persists the session's requested chains, which its WalletConnect connector needs to recognize a restored session. A saved connection without a live session must still allow a fresh wallet choice.

## Deployment

Railway builds with Railpack (`yarn build`) and serves `dist/frontend/browser` with Caddy using [Caddyfile](Caddyfile). Caddy also forwards `/api/*` to the backend, so portal cookies stay on the frontend origin, and marks HTML routes `no-cache`.

- The `package.json` engines field selects Node 22. If Railway has a `RAILPACK_NODE_VERSION` override, set it to `22` too.
- Add the deployed origin to the Reown dashboard's allowlist.

## EVM Wallet Connections

Reown AppKit owns WalletConnect, injected-wallet discovery, and Coinbase connectors through one shared Wagmi adapter. It uses the existing Reown/WalletConnect project ID and the page's current origin for Bouncer metadata. Ensure any origin allowlist in the Reown dashboard includes the deployed frontend domain.

The public project ID and shared app metadata live in `src/app/services/evm-wallet.config.ts`.

Keep AppKit 1.8.24 on the Wagmi Core 2.22.1 / Connectors 6.2.0 combination. The Yarn resolution for `@wagmi/connectors` also pins AppKit's broad optional dependency, which otherwise selects Connectors 8 and expects Wagmi 3. A Wagmi 3 upgrade on AppKit 1.8.24 was tried and reverted on November 16, 2026 (#155, #156); upgrade together with AppKit 2.0 instead, as tracked in the [optional backlog](../docs/plans/optional-features.md#dependency-maintenance). See [Reown's installation guide](https://docs.reown.com/appkit/javascript/core/installation).

Base Account (`base-account.connector.ts`) starts new connections on Base and restores saved sessions without reopening the Coinbase popup. On phones, AppKit lists Base Account under its shared Coinbase Wallet entry and connects it through the Coinbase Wallet SDK connector; `utils/smart-wallet.util.ts` recognizes both. When a Base Account is connected, the verify page and the member portal show a network chooser; ordinary wallets don't need one because key proofs count on every network. See [smart-wallet verification](../docs/smart-wallet-verification.md).

Automatic reconnection reuses an approved wallet session rather than disconnecting it whenever a verification link loads. Each verification still requires signing its fresh EIP-712 challenge; a restored session does not verify the member. The connected address, **Change wallet** and **Disconnect wallet** are shown before signing (the member portal's Add wallet has the same buttons). Changing wallets deliberately disconnects through AppKit before opening the picker. Switching between wallet families does not tear down the EVM session. Email/social login, swaps, on-ramp, send/receive, and account history are disabled. Xverse and UniSat continue to use their separate Bitcoin connection flow.

Connection errors from the picker appear on the verification page, including guidance for pending requests and connection-service failures. Browser-to-wallet app launches still depend on the mobile browser and installed wallet. Test Rainbow on a real Android/iOS device before treating a desktop browser check as confirmation of mobile compatibility.

Keep the explicit `module` resolution condition in both Angular build configurations. WalletConnect's package has separate ESM and CommonJS exports; resolving the wrong form can compile successfully but fail during provider initialization. The production browser smoke test covers this path.

### Mobile connection diagnostics

Open `/wallet-check` on the affected device to test the same AppKit connection independently of verification. **Start connection** opens the normal wallet picker. After a failed attempt, return to the page and use **Copy connection details**.

The **WalletConnect only** link opens `/wallet-check?mode=direct`. It uses the same Reown project, origin, metadata, and Sign Client 2.23.7, but bypasses AppKit, Wagmi, and automatic app launching. Start the test, then tap **Open Rainbow**. Its one-chain connection request grants no transaction method and requests no signatures. The diagnostic session uses a separate storage prefix so it cannot delete the verification app's session. Reload either mode to check session restoration; **Disconnect test** deliberately ends the session used by that mode (the Bouncer-kit mode shares the normal verification connection).

Both modes record elapsed times, browser visibility, relay events, and session approval. They never call the verification backend or change member roles. Copied details omit pairing URIs, credentials, wallet addresses, session topics, and encrypted message bodies; they remain local unless the tester shares them. Success in direct mode but failure in normal mode narrows the issue to the adapter, request scope, storage, or app-launch flow. Failure in both modes points to their shared protocol, wallet, project, or network path; it does not identify the exact cause on its own.
