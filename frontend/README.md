# Bouncer Frontend

Angular verification app for Discord users following `/verify/:data` links.

## Stack

- Angular 21
- TypeScript 5.9
- SCSS
- wagmi 3 + Reown AppKit + viem

## What It Does

- Opens verification links generated by the Discord bot
- Connects wallets through WalletConnect, injected wallets, and Coinbase Wallet
- Signs EIP-712 verification payloads
- Sends verification requests to the backend API
- Connects Xverse or UniSat Bitcoin mainnet Taproot Ordinals wallets and signs BIP-322 ownership messages
- Opens mobile verification links inside UniSat through its HTTPS `openDapp` app link

## Requirements

- Node.js `22.12+` (22.x)
- Yarn `1.22.x`

## Environment Files

- [src/env/env.ts](src/env/env.ts): production/default values
- [src/env/env.dev.ts](src/env/env.dev.ts): used by the Angular development build via file replacement

The checked-in development config currently points at:

```ts
apiUrl: 'http://localhost:3200/api'
```

So either:
- run the backend locally on port `3200`, or
- update [env.dev.ts](src/env/env.dev.ts) for your local backend URL

## Local Development

Install dependencies:

```bash
yarn install
```

Run the Angular dev server:

```bash
yarn ng serve
```

Then open `http://localhost:4200`.

## Scripts

```bash
yarn ng serve       # Angular dev server (default: localhost:4200)
yarn build          # Production build to dist/frontend
yarn watch          # Development build in watch mode
yarn start          # Serve dist/frontend/browser on $PORT
yarn test           # Karma test runner
```

For a headless local/CI-style test run:

```bash
yarn test --watch=false --browsers=ChromeHeadless
```

Check the production wallet bundle with an installed Chrome/Chromium browser:

```bash
yarn build
CHROME_BIN=/path/to/chrome yarn test:wallet-smoke
```

This uses simulated wallets, backend responses, and relay traffic. It verifies EIP-712 signatures on desktop/mobile layouts, repeat visits, Android Rainbow app links, and retries with a saved connection from a previous page. It does not use real wallets or API credits. Screenshots are written to a temporary directory.

AppKit and Wagmi restore approved EVM wallet sessions together across visits. Wagmi also persists the session's requested chains, which its WalletConnect connector needs to recognize a restored session. A saved connection without a live session must still allow a fresh wallet choice.

## Deployment

This app is deployed as a built static bundle plus a simple static file server:

```bash
yarn build
yarn start
```

Notes:
- `yarn start` expects `dist/frontend/browser` to already exist.
- On Railway, prefer `Railpack` instead of deprecated `Nixpacks`.
- The frontend's `package.json` selects Node 22. If Railway has a `RAILPACK_NODE_VERSION` or `NIXPACKS_NODE_VERSION` override, set it to `22` as well.

## EVM Wallet Connections

Reown AppKit owns WalletConnect, injected-wallet discovery, and Coinbase connectors through one shared Wagmi adapter. It uses the existing Reown/WalletConnect project ID and the page's current origin for Bouncer metadata. Ensure any origin allowlist in the Reown dashboard includes the deployed frontend domain.

Automatic reconnection reuses an approved wallet session rather than disconnecting it whenever a verification link loads. Each verification still requires signing its fresh EIP-712 challenge; a restored session does not verify the member. The connected address and a **Change wallet** button are shown before signing. Changing wallets deliberately disconnects through AppKit before opening the picker. Switching between Ethereum and Bitcoin does not tear down the EVM session. Email/social login, swaps, on-ramp, send/receive, and account history are disabled. Xverse and UniSat continue to use their separate Bitcoin connection flow.

Connection errors from the picker appear on the verification page, including guidance for pending requests and connection-service failures. Browser-to-wallet app launches still depend on the mobile browser and installed wallet. Test Rainbow on a real Android/iOS device before treating a desktop browser check as confirmation of mobile compatibility.

Keep the explicit `module` resolution condition in both Angular build configurations. WalletConnect's package has separate ESM and CommonJS exports; resolving the wrong form can compile successfully but fail during provider initialization. The production browser smoke test covers this path.
